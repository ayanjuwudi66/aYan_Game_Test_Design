# Game Test Design

## 使用前提

不要猜测未给出的规则。先明确功能名称、被测类型、范围和测试目的；再索取 PRD/策划案/原型/接口/配置表，或让用户按结构化模板补充。用户材料必须原样保留，推导出的内容单列并标记为“待确认”。

### 图片材料识别（AI 多模态）

用户上传的需求材料**可能包含图片**（UI 原型图、交互示意图、数值表截图、竞品截图等）。本 skill 采用 **AI 多模态读图**方式识别，不依赖外部 OCR/视觉 API：

- **识别范围**：图片中的文字（标题、按钮文案、数值）、UI 元素结构、布局关系、状态展示。只要图内信息影响规则判定，就必须读取。
- **处理动作**：把图内可提取的规则**转写成结构化文字**，纳入「读取需求材料」环节，作为需求材料的组成部分。
- **来源标注（关键，延续严谨原则）**：图内**直接可见**的信息归入 **Part A（材料原样提取）**；基于图的**推断**（如"这个按钮大概代表某功能"）归入 **Part B（待确认）**，绝不写成确定预期。
- **多图对应**：一张图可能对应多个行为/多个节点。转写时按"每张图 + 涉及的行为/节点"分别记录，便于后续对应用例。
- **不可识别时**：图片模糊、无有效文字、或图内规则存在歧义时，明确告知"该图信息无法可靠提取"，并请求用户补充文字说明，不得臆测。
- **转写产物落盘**：图片转写的文字整理进对应行为的推演文档（Part A / Part B 分栏），作为用例来源。

## SOP

1. **明确被测对象**：确认功能、角色/权限、范围（含不覆盖项）和目的。
2. **读取需求材料**：从材料（**含文字与图片**）提取前置、输入、规则、状态流转、输出、异常和非功能要求。图片材料按上方「图片材料识别」规则转写并标注来源。提供配置表时才检查类型、空值、引用、热更、关联与极值；未提供则声明配置风险未覆盖。
3. **边界与规则确认**：输出 Part A（材料原样提取）和 Part B（主动补充，全部待确认）。主动补充按七问、L1-L7、影响面、状态机、边界、并发时序、失败回滚七条来源推导，并标注级别、来源、问题、依据。

用户拍板后再生成正式用例。循环无天然终态时，读取 [references/baseline-table.md](references/baseline-table.md) 采用或确认 N/T 截断值。

## 核心推演

- 把功能视为状态机，沿时间轴覆盖“节点、边、异常注入、分支”，每个节点按七问重新检查。

## 粒度规则（易错点，必须遵守）

- **一个行为 = 一份独立推演文档。不要把多个行为合并进一张表。** 判断标准：两个行为的失败回滚清单不同，就是两个行为。合并会导致不同类型缺陷互相掩盖。
- 单行为内部按**原子状态变化**拆节点。判断标准：某节点失败后的回滚清单与其他节点不同，就该独立成节点。
- **资源扣减、计数写入、持久化与释放锁必须各自独立成节点**——它们分别对应「丢数据」「可无限刷」「后续操作全失败」三类不同缺陷。
- 每个节点独立走完七问，不与其他节点共用答案；只保留该节点**实际命中**的 L1-L7 层级，不照抄八行。
- 每个节点对影响面 8 类逐类判定 ✔ / ✖ / ？，✖ 也要能说出依据。
- 文档开头必须先写**行为边界**（起始边界、终止边界、不属于本行为的相邻行为清单），否则无法保持独立。

## 继续推演

- 主链路先输出骨架，再询问是否允许生成 Excel；获准后展开 L1-L7 与影响面扫描。
- L1/L2/L5 用例备注建议叠加弱网复测；重点检查状态残留、动画卡死、本地预表现与服务器回滚不一致。
- 影响面是与七问正交的横向维度：自身、队友、敌对玩家、中立单位、环境场景、观战者、服务器全局、AI/召唤物。
- 绝不把推断、概率、仓库内部逻辑或未定版策划细节写成确定预期。
- 图片转写的信息与文字材料同等参与推演：图内可见规则进 Part A，基于图的推断进 Part B；图片涉及的每个行为单独标注其图源，保证用例可追溯到具体截图。
