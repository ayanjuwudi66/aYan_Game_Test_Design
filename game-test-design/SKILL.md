# Game Test Design

## 使用前提

不要猜测未给出的规则。先明确功能名称、被测类型、范围和测试目的；再索取 PRD/策划案/原型/接口/配置表，或让用户按结构化模板补充。用户材料必须原样保留，推导出的内容单列并标记为“待确认”。

## 触发与降级

- **适用**：有明确被测功能/玩法 + 至少一份需求材料（PRD/策划案/原型/配置表）。
- **不适用**：纯一句话需求、无任何材料，或需求本身是性能/安全/兼容/数值专项。
- **材料不足时**：不硬走完整 SOP，先产出「最小可测清单骨架」+「待补材料清单」（见 [templates/最小可测清单骨架.md](templates/最小可测清单骨架.md)、[templates/待补材料清单.md](templates/待补材料清单.md)），请用户补充后再展开七问/L1-L7/影响面。

## 边界（不涉及，转交专项）

本 skill 只做功能/玩法/实时交互的测试设计。以下四类不覆盖：

| 不覆盖 | 观察到风险时的处理 |
|---|---|
| 性能（帧率、内存、对象池、日志/网络包量） | 记录 → 转交性能专项 |
| 安全（外挂、透视、无敌、秒杀、客户端篡改） | 记录 → 转交安全/反作弊专项 |
| 兼容性（切后台、来电、锁屏、低电量、权限弹窗） | 记录 → 转交兼容性专项 |
| 数值平衡（伤害公式、经济产出、成长曲线） | 只测数值的「展示正确性」→ 平衡本身转交数值策划/专项 |

注：L6-b 网络异常（弱网）**保留**——它是功能正确性观察点（回滚、表现与服务器一致），但「专项弱网测试」（量化延迟、丢包率）转交网络专项。

## 运行依赖

- Python 3：`openpyxl`（生成用例 Excel，必须）
- OCR 兜底（可选）：`rapidocr-onnxruntime`

## 工作方式（协作前置 + 及时反馈，最高优先级）

1. **先对齐颗粒度，再动手**：拿到需求后，第一时间与用户对齐「按什么切分、覆盖到多深、边界在哪、哪些明确不覆盖」，确认后再展开推演。宁可先问清 3 个问题，不要做完返工 3 个版本。
2. **一次性读透材料，不反复读试错**：仔细、反复阅读需求/文档/图片，把规则、边界值、特殊情况判定一次吃全。不要靠反复读取同一份数据来“试”——读一次就要读全；反复重读消耗上下文且不增加信息。
3. **疑问即时抛，矛盾即时反馈**：读到任何疑问点、上下文逻辑矛盾、口径不一致、图与文字对不上，立即向用户提出并确认预期结果，不要揣测后闷头继续做。
   - **"图读不了"属于必须即时抛的情形**：一见读不动就当场说，不许闷头继续，也不许只在交付文件里写一笔留痕。完整要求见下方「图片材料识别 → 告知义务」。
4. **未拍板项显式沉淀**：边界值、特殊情况判定、未定数值等，凡未拍板的，一律单列《待确认项清单》，绝不在用例预期中写死推断值。
   - **清单字段契约（7 列，与脚本 `pending` JSON 键一致）**：`编号 | 分类 | 待确认 | 来源 | 影响 | 默认处理 | 状态`。其中「待确认」列按四要素写（讨论问题 / 已知口径（材料·图源·已有拍板）/ 不确认后果 / 建议问法），「影响」列写明影响的行为/用例。「默认处理」供参考，「状态」留「待确认 / 已确认」。
   - **对外沟通时**：把《待确认项清单》按「阻塞级别 + 按行为分组」重排后另存一份《待与策划讨论清单》（对外视图，不单独维护数据）。
   - **必须标阻塞级别**：`阻塞`（不确认则预期写死不了或用例无法执行）/ `影响`（能测但结论可能变）/ `补充`（细节完善）/ `知会`（仅需对齐）。用户时间有限，级别决定开会顺序。
   - **按行为分组，不按分类平铺**：让用户一眼看出"哪个行为是重灾区"，便于整块约策划过，而不是零散问。
   - **数值类与文档缺口分开标**：数值待定（问一句就能回填）与"材料本身缺一行/两处口径冲突"（需要策划补文档）处理方式不同，混在一起会拖慢沟通。

### 图片材料识别

用户上传的需求材料可能含图片，图内信息常为规则唯一出处，必须读到。完整降级链（L0 多模态直读含重试 → L1 OCR → L2 像素分析 → L3 用户代读）、xlsx 内嵌图导出、来源 A/B 标注与告知义务，见 [references/image-recognition.md](references/image-recognition.md)。

要点：每级结论必须引用落盘产物，「没有产物 = 这一级未走过」；任何一张图没读全必须主动告知用户，不得含糊带过。

### UI 表现校验与 icon 图集自检

每个行为节点用例须同时覆盖功能与 UI 表现两个维度。四类断言、多态多变体、独立 icon 图集索引的完整规则见 [references/ui-assertion.md](references/ui-assertion.md)。

## SOP

1. **明确被测对象**：确认功能、角色/权限、范围（含不覆盖项）和目的。
2. **读取需求材料**：从材料（**含文字与图片**）提取前置、输入、规则、状态流转、输出、异常和非功能要求。图片材料按上方「图片材料识别」规则转写并标注来源。提供配置表时才检查类型、空值、引用、热更、关联与极值；未提供则声明配置风险未覆盖。
   - **2a 先建图源清单（前置动作）**：清点材料中**全部**图片，逐张登记 `文件名 | 尺寸 | 锚点位置 | 预估承载内容`。xlsx 内嵌图用 `zipfile` 解包 `xl/media/*` 取全量列表，不要用 openpyxl 的 `img._data()`（会报 I/O closed）。**没有这张清单就无从判断"读完了没"，不得进入后续步骤。**
   - ⚠️ **读图门禁**：凡材料含图且图内可能是规则唯一出处，必须逐张走完降级链——**多模态直读（L0，含重试）→ OCR → 像素分析 → 请用户代读**（见上方「图片材料识别」各条）。
     1. **进入第 3 步前，必须先输出图源读取结果并声明读取率：已读 N / 共 M。**
     2. **读取率 = 100%** → 正常进入第 3 步。
     3. **读取率 < 100%** → **停在第 2 步**，向用户报告：未读图清单 + 已尝试的级别与落盘产物 + 未读原因。由用户三选一：① 补料后继续 ② 带缺口继续（缺口必须登记进《待确认项清单》）③ 该图相关用例暂停。**未经用户选择，不得默认带缺口继续。**
3. **边界与规则确认**：输出 Part A（材料原样提取）和 Part B（主动补充，全部待确认）。主动补充按七问、L1-L7、影响面、状态机、边界、并发时序、失败回滚七条来源推导，并标注级别、来源、问题、依据。

用户拍板后再生成正式用例。循环无天然终态时，读取 [references/baseline-table.md](references/baseline-table.md) 采用或确认 N/T 截断值。

## 核心推演

- 把功能视为状态机，沿时间轴覆盖“节点、边、异常注入、分支”，每个节点按七问重新检查。

## 粒度规则（易错点，必须遵守）

- **一个行为 = 一份独立推演文档。不要把多个行为合并进一张表。** 判断标准：两个行为的失败回滚清单不同，就是两个行为。合并会导致不同类型缺陷互相掩盖。
- 单行为内部按**原子状态变化**拆节点。判断标准：某节点失败后的回滚清单与其他节点不同，就该独立成节点。
- **资源扣减、计数写入、持久化与释放锁必须各自独立成节点**——它们分别对应「丢数据」「可无限刷」「后续操作全失败」三类不同缺陷。
- 每个节点独立走完七问，不与其他节点共用答案；只保留该节点**实际命中**的 L1-L7 层级，不照抄八行。
- 每个节点对影响面 8 类逐类判定 ✔ / ✖ / ？，✖ 也要能说出依据。
- 文档开头必须先写**行为边界**（起始边界、终止边界、不属于本行为的相邻行为清单），否则无法保持独立。

## 输出约定（交互键类系统用例表）

生成**可直接交付的用例 Excel** 时，遵循三条约定：

1. **行为粒度 = 单个可交互按键/操作**：以"一个可交互按键/一次操作"为单位拆组（如 拜访、邀请、跟随、换一批 各自成组），不把多个键合并进同一行。每组内部四段覆盖：
   - **显隐条件**：什么状态出现、什么状态消失，逐条件列全（不要只写"有显示"，要写"XX 状态不显示"）
   - **图标校验**：icon 资源与样式是否正确（含独立小图集校验）
   - **成功流**：点击后正常流转的步骤与结果
   - **失败流**：状态变化、连点、弱网、回滚等失败路径
2. **输出格式固定（8 列）**：`功能 | 测试点 | 前提条件 | 操作步骤 | 预期结果 | 备注 | 优先级 | 结果`；备注与结果列**留空**交执行人填；相同功能可合并单元格。列序按执行时序排：优先级执行前看（排期依据）、结果执行后填（产出），故结果置于末列，执行时视线从步骤一路向右到底打勾，不用回头。
   - **前提条件必须独立成列**，不得与操作步骤混写。历史写法把前置塞进操作步骤首句（`前置：<条件>。1. …`），导致一列两责、执行人分不清"要准备什么"和"要做什么"，也不便于按前置批量准备数据。
   - 前提条件写**状态与环境**（账号关系、次数余量、时段、对象状态、他人占用情况等），操作步骤只写**执行动作**（`1. … 2. …`），两者不得互串。
   - 无前置的用例前提条件列填"无"，不要留空，避免执行时误判为"漏写"。
   - **单元格内换行**：前提条件/操作步骤/预期结果含 `1. … 2. … 3. …` 多条时，必须在**同一个单元格内逐条换行**，不许挤成一行靠列宽折行——折行会把序号折断、执行人一眼看不出总共几步。脚本 `cell_break()` 已自动处理（序号后紧跟数字不算序号，避免切坏 3.5 秒、40.50% 这类小数）。
3. **未确认规则不混入预期**：凡规则未拍板（如具体数值、兜底策略），一律单列《待确认项清单》（7 列契约见「工作方式」第 4 条），确认后回填，绝不在用例预期中写死推断值。
   - 对外沟通时，把《待确认项清单》按「阻塞级别 + 按行为分组」重排后另存为**《待与策划讨论清单》**（对外视图，不单独维护数据）。
4. **交付 Excel 是「三件套」**：`测试用例` + `待确认项清单` + `图源说明` 三者一并产出，缺一不可。待确认项与图源说明不是"可选附件"，是交付物的必要组成，不要等用例做完再手工补。脚本 `scripts/gen_testcase_xlsx.py --format delivery` 已支持一步生成三件套（输入 `{"cases":[...], "pending":[...], "img_notes":[...]}`，`pending` 键 = `编号/分类/待确认/来源/影响/默认处理/状态`）。

## 继续推演

- 主链路先输出骨架，再询问是否允许生成 Excel；获准后展开 L1-L7 与影响面扫描。
- L1/L2/L5 用例备注建议叠加弱网复测；重点检查状态残留、本地预表现与服务器回滚不一致。（动画卡死等表现性能问题 → 记录转交性能专项，见「边界」）
- 影响面是与七问正交的横向维度：自身、队友、敌对玩家、中立单位、环境场景、观战者、服务器全局、AI/召唤物。
- 绝不把推断、概率、仓库内部逻辑或未定版策划细节写成确定预期。
- 图片转写的信息与文字材料同等参与推演：图内可见规则进 Part A，基于图的推断进 Part B；图片涉及的每个行为单独标注其图源，保证用例可追溯到具体截图。
