# Game Test Design

## 使用前提

不要猜测未给出的规则。先明确功能名称、被测类型、范围和测试目的；再索取 PRD/策划案/原型/接口/配置表，或让用户按结构化模板补充。用户材料必须原样保留，推导出的内容单列并标记为“待确认”。

## 工作方式（协作前置 + 及时反馈，最高优先级）

1. **先对齐颗粒度，再动手**：拿到需求后，第一时间与用户对齐「按什么切分、覆盖到多深、边界在哪、哪些明确不覆盖」，确认后再展开推演。宁可先问清 3 个问题，不要做完返工 3 个版本。
2. **一次性读透材料，不反复读试错**：仔细、反复阅读需求/文档/图片，把规则、边界值、特殊情况判定一次吃全。不要靠反复读取同一份数据来“试”——读一次就要读全；反复重读消耗上下文且不增加信息。
3. **疑问即时抛，矛盾即时反馈**：读到任何疑问点、上下文逻辑矛盾、口径不一致、图与文字对不上，立即向用户提出并确认预期结果，不要揣测后闷头继续做。
4. **未拍板项显式沉淀**：边界值、特殊情况判定、未定数值等，凡未拍板的，一律单列《待确认项清单》，绝不在用例预期中写死推断值。

### 图片材料识别（多模态优先，OCR 与像素分析兜底）

用户上传的需求材料**可能包含图片**（UI 原型图、交互示意图、数值表截图、竞品截图等），图内信息常为规则的唯一出处，**必须读到**：

- **首选**：AI 多模态直读。图内文字、UI 结构、布局关系、状态展示一并转写。
- **兜底（模型不支持读图时，禁止直接放弃）**：改用工程手段提取，两条路径覆盖两类信息：
  1. **图内文字 → OCR**：`pip install rapidocr-onnxruntime`（自带模型，无需系统依赖）。对原图 + 放大 3x/5x 各跑一遍，按行聚类、同位置保留置信度高者，可显著提升小字与手写体准确率。
  2. **视觉状态 → 像素统计与差异定位**：无文字的图（纯 icon/纯 UI）用平均亮度、平均饱和度、**近灰像素占比**、主色分布做量化；判定两张图是否为"同一界面的两个状态"时，做差分投影扫描，输出差异区块 bounding box 定位元素位置，再对该区域做亮度/饱和/灰化对比。
- **xlsx 内嵌图导出**：openpyxl 的 `img._data()` 会报 `I/O operation on closed file`，改用 `zipfile` 直接解包取 `xl/media/*`；再用 `xl/drawings/drawing1.xml` + `_rels` 解析 `twoCellAnchor` 的 col/row，建立「图 ↔ 工作表单元格 ↔ 邻近文字」映射，据此判断每张图的语义归属。
- **处理动作**：把图内可提取的规则**转写成结构化文字**，纳入「读取需求材料」环节，作为需求材料的组成部分。
- **来源标注（关键，延续严谨原则）**：图内**直接可见**的信息归入 **Part A（材料原样提取）**；基于图的**推断**（如"这个按钮大概代表某功能"）归入 **Part B（待确认）**，绝不写成确定预期。
- **多图对应**：一张图可能对应多个行为/多个节点。转写时按"每张图 + 涉及的行为/节点"分别记录，便于后续对应用例。
- **锚点可能错位**：图片在文档中的位置（行号/单元格锚点）与图的实际内容可能不一致（策划把图放错位置、或一张图被挪作他用）。读图后必须**以图的实际内容为准**重新判定语义归属，再对照邻近文字确认，不能盲信文档锚点行号。
- **不可识别时**：OCR 与像素分析均无法提取、图像模糊、或图内规则存在歧义时，明确告知"该图信息无法可靠提取"并请求用户补充，不得臆测。**仅当两条兜底路径都走过之后**才可下此结论；"模型不支持读图"本身不构成放弃的理由。
- **兜底提取到的信息同样按 A/B 分栏**：OCR 直接读出的文字进 Part A；由像素指标反推的结论（如"暗态 = 压暗加降饱和"）进 Part B 并写明推导依据。
- **转写产物落盘**：图片转写的文字整理进对应行为的推演文档（Part A / Part B 分栏），作为用例来源。**图内 UI（icon/布局/文案/状态视觉）另整理为"UI 表现清单"，作为 UI 用例的断言基准。**

### UI 表现校验（强制维度，防"只验逻辑不验界面"）

**每个行为节点的用例必须同时覆盖「功能/数据/状态」与「UI 表现」两个维度，缺一不可。** 只验证"列表加载了、状态对了"而不断言"界面长什么样"，属于不完整用例（历史高频缺陷：icon 用错资源、按钮该亮没亮、文案与设计稿不一致、布局错位）。

判定规则：

- **凡节点上有可见 UI/icon/文案产出，必须单独生成 UI 用例**，并**插入该节点所属行为的流程中**（不单独堆在末尾，跟着行为走，便于按对象一条龙测完）。
- UI 用例的四类断言（按实际命中选用，不照抄四类）：
  1. **图标/资源正确性**：用的是不是设计稿/原型图中那个 icon（形状、颜色、风格），对照图源编号。
  2. **显隐与状态视觉**：该亮/该灰/该隐藏/加载中/成功/失败各自的视觉表现。
  3. **布局与文案**：位置、对齐、间距；文案一字不差（欢迎词、提示语、空状态、按钮文字）。
  4. **状态切换视觉**：列表刷新、切换、进出场时的视觉过渡，无错位/闪烁/残留。
- **同一 UI 元素的多态/多变体必须分别覆盖**：一个元素可能按「状态 × 样式变体」呈现多种形态（如信息卡片分 成熟/成长 × 变异/未变异 × 标准/简化）。读图后先枚举该元素在材料中出现的**全部变体**，逐变体断言，不能只验一种默认样式。（历史高频缺陷：只测了成熟态，漏掉成长态；只测了未变异，漏掉变异后新增的字段与标签。）
- **UI 断言基准 = 需求材料中的图片（UI 原型图、竞品截图、示意图）**。凡材料含图，UI 用例必须标注对照图源（如"如图 image50：当前页签卡右侧交互键为 X/Y/Z 组合"）；图中可见→Part A 基准，推断→Part B 待确认。
- 纯逻辑节点（纯服务端计算、无可见 UI 变化）可不产 UI 用例，但须说明"本节点无 UI 产出"。

**常见遗漏检查**（生成用例后自查，任一命中即补 UI 用例）：
- [ ] 列表/卡片上的 icon、状态标志（如可采收标志、农场主标注）只验了显隐，没验资源对不对
- [ ] 空状态/加载失败/成功反馈只有文案预期，没有"icon + 布局"预期
- [ ] 弹窗/浮层（采收设置、每日限额、确认框）只验了功能，没验视觉结构
- [ ] 交互键（拜访/加好友/请离/跟随）没对照图源确认 icon 形状与组合
- [ ] **独立小尺寸 icon 资源图集已建索引并对应到用例**（见下条"icon 资源图集自检"）

### icon 资源图集自检（针对带原型的需求）

游戏需求材料中常见**两类图**：整页 UI 截图（布局/位置基准）+ **小尺寸独立 icon 资源图**（icon 资源正确性的基准）。后者极易被忽略——文字里"显示 XX icon"对应的小图常被当作"装饰"跳过。

自检步骤（生成用例前一次性完成，结果作为用例图源索引）：

1. **遍历所有图片**，按尺寸分两类：整页截图（>300px）+ 独立 icon（<200px）
2. **独立 icon 图集逐个识别**：根据视觉+文字规则做映射（如 DNA=变异、握手=邀请、人+加号=加好友、人+出箭头=请离等）。**这一步不可跳过——跳过就会出现"文字里说要显示 icon，用例里却没校验 icon 资源"**。
3. **建立图源索引文档**，明确每张图对应什么用例断言基准（icon 资源 / 布局 / 文案 / 状态视觉）。
4. 后续每条 UI 用例**必须引用图源**（按断言类型引用对应图：icon→独立 icon 图，布局→整页截图）。**对每条文字里提到的"XX icon"断言项，确认有对应的独立 icon 图可引用；如无图，在备注标"无独立 icon 图源，文案断言替代"**。
5. 文字+图源两者**双校验**：文字给了规则（图标存在性/显隐），图给了视觉（资源/位置）。**只用文字不查图 = 漏一半；只用图不读文字 = 漏规则**。

## SOP

1. **明确被测对象**：确认功能、角色/权限、范围（含不覆盖项）和目的。
2. **读取需求材料**：从材料（**含文字与图片**）提取前置、输入、规则、状态流转、输出、异常和非功能要求。图片材料按上方「图片材料识别」规则转写并标注来源。提供配置表时才检查类型、空值、引用、热更、关联与极值；未提供则声明配置风险未覆盖。
   - ⚠️ **读图是硬性步骤**：凡材料含图且图内可能是规则唯一出处，必须读图（多模态直读 → OCR → 像素分析），三步穷尽前**不得以"模型不支持读图"为由跳过**。本次流程中若发现"读不了图"，先自查是否真的穷尽了兜底路径，再下结论。
3. **边界与规则确认**：输出 Part A（材料原样提取）和 Part B（主动补充，全部待确认）。主动补充按七问、L1-L7、影响面、状态机、边界、并发时序、失败回滚七条来源推导，并标注级别、来源、问题、依据。

用户拍板后再生成正式用例。循环无天然终态时，读取 [references/baseline-table.md](references/baseline-table.md) 采用或确认 N/T 截断值。

## 核心推演

- 把功能视为状态机，沿时间轴覆盖“节点、边、异常注入、分支”，每个节点按七问重新检查。

## 粒度规则（易错点，必须遵守）

- **一个行为 = 一份独立推演文档。不要把多个行为合并进一张表。** 判断标准：两个行为的失败回滚清单不同，就是两个行为。合并会导致不同类型缺陷互相掩盖。
- 单行为内部按**原子状态变化**拆节点。判断标准：某节点失败后的回滚清单与其他节点不同，就该独立成节点。
- **资源扣减、计数写入、持久化与释放锁必须各自独立成节点**——它们分别对应「丢数据」「可无限刷」「后续操作全失败」三类不同缺陷。
- 每个节点独立走完七问，不与其他节点共用答案；只保留该节点**实际命中**的 L1-L7 层级，不照抄八行。
- 每个节点对影响面 8 类逐类判定 ✔ / ✖ / ？，✖ 也要能说出依据。
- 文档开头必须先写**行为边界**（起始边界、终止边界、不属于本行为的相邻行为清单），否则无法保持独立。

## 输出约定（交互键类系统用例表）

生成**可直接交付的用例 Excel** 时，遵循三条约定：

1. **行为粒度 = 单个可交互按键/操作**：以"一个可交互按键/一次操作"为单位拆组（如 拜访、邀请、跟随、换一批 各自成组），不把多个键合并进同一行。每组内部四段覆盖：
   - **显隐条件**：什么状态出现、什么状态消失，逐条件列全（不要只写"有显示"，要写"XX 状态不显示"）
   - **图标校验**：icon 资源与样式是否正确（含独立小图集校验）
   - **成功流**：点击后正常流转的步骤与结果
   - **失败流**：状态变化、连点、弱网、回滚等失败路径
2. **输出格式固定**：`功能 | 测试点 | 操作步骤 | 预期结果 | 备注 | 结果 | 优先级`；备注与结果列**留空**交执行人填；相同功能可合并单元格。
3. **未确认规则不混入预期**：凡规则未拍板（如具体数值、兜底策略），一律单列《待确认项清单》（含来源、影响行为、默认处理、状态），确认后回填，绝不在用例预期中写死推断值。
4. **交付 Excel 是「三件套」**：`测试用例` + `待确认项清单` + `图源说明` 三者一并产出，缺一不可。待确认项与图源说明不是"可选附件"，是交付物的必要组成，不要等用例做完再手工补。脚本 `scripts/gen_testcase_xlsx.py --format delivery` 已支持一步生成三件套（输入 `{"cases":[...], "pending":[...], "img_notes":[...]}`）。

## 继续推演

- 主链路先输出骨架，再询问是否允许生成 Excel；获准后展开 L1-L7 与影响面扫描。
- L1/L2/L5 用例备注建议叠加弱网复测；重点检查状态残留、动画卡死、本地预表现与服务器回滚不一致。
- 影响面是与七问正交的横向维度：自身、队友、敌对玩家、中立单位、环境场景、观战者、服务器全局、AI/召唤物。
- 绝不把推断、概率、仓库内部逻辑或未定版策划细节写成确定预期。
- 图片转写的信息与文字材料同等参与推演：图内可见规则进 Part A，基于图的推断进 Part B；图片涉及的每个行为单独标注其图源，保证用例可追溯到具体截图。
